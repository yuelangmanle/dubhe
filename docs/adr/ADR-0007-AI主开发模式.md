# ADR-0007: 开发模式——AI 主开发 + 人类验证

- 状态：Accepted
- 日期：2026-10-29
- 决策者：你（产品负责人）
- 关联：DUBHE-DEV-000 §7

## 背景

本项目没有团队。**代码全部由 AI 编写，人类只做验证、优先级排序与最终拍板。**

这不是"用 Copilot 辅助"，而是把 AI 当作唯一实现者。它带来两个直接后果：

1. 原按 8 人 × 63 周排的计划完全失效（人力模型不存在了）；
2. 传统的质量保障（code review、结对、口头传承）全部失效，必须换成别的东西。

## 决策

采用 **Round 循环**作为项目的基本时间单位：

```
AI 交付一批可运行增量 → 人类跑一条命令（≤5min）→ 回传输出 → AI 分析 → 下一轮
```

并配套三条硬约束：

1. **可自证**：没有第二人 review，正确性只能靠可执行测试（parity / fuzz / 回归）。写不出测试的功能不算完成。
2. **一条命令可验证**：每轮交付必须附一条可复制的命令与预期输出形态。若验证需要人类先读代码，视为交付不合格。
3. **性能只认真机**：AI 不能在自己的环境跑目标硬件，所有性能结论必须由人类回传，禁止用"理论上更快"结案。

## 备选方案

| 方案 | 优点 | 缺点 | 为什么没选 |
| --- | --- | --- | --- |
| 按人周排期（v1 方案） | 传统、易沟通 | 人力模型不存在，排出来的日期全是假的 | 不成立 |
| 只给里程碑不给时间 | 不撒谎 | 无法判断是否失控 | 缺少节拍 |
| **Round 制**（本方案） | 节拍由"可验证增量"定义，不依赖人力估算 | 总时长不确定性大，取决于验证往返 | **本方案** |

## 后果

正面：

- 里程碑的定义从"人干多少活"变成"什么东西被验证通过"，更抗估算误差。
- 每一轮都有明确的验收物，不会出现"做了很多但说不清做了什么"。
- 决策全部落盘在 ADR / 进度书，不依赖对话记忆。

负面 / 代价：

- **最大瓶颈是人类验证的往返速度**，不是编码速度。人类忙一周，项目就停一周。
- AI 无长期记忆，跨轮次一致性靠文档维持，文档质量直接决定项目质量。
- 架构级错误可能潜伏很久（没人 review），只能靠测试与基准兜底。
- 无法评估"手感"类体验问题，所以 M5 前不做 UI。

需要跟进：

- [ ] 每轮交付物必须含：变更说明 + 一条验证命令 + 预期输出 + 回传模板
- [ ] 关键模块先写接口与测试，再写实现（防止大范围返工）
- [ ] 每个里程碑结束做一次"文档校准"，确认 ADR 与实际实现一致

## 复审条件

- 引入第二个人（哪怕是兼职 reviewer）时，重新评估是否需要恢复常规 PR review；
- 若连续 3 个 Round 的验证都失败（说明自证机制不足），必须先补测试基建再继续做功能。
