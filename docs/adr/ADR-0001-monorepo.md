# ADR-0001: 采用 monorepo

- 状态：Accepted
- 日期：2026-10-29
- 决策者：Tech Lead
- 关联：AETHER-DEV-000 §6.1

## 背景

项目同时包含 C++ 引擎内核、C ABI 与语言绑定、macOS 宿主、Android 宿主、Python 工具链与基准套件。这些部分的接口变更频率极高：引擎每两周就可能改一次 ABI，而宿主必须同步跟上。

若拆成多仓，每次接口变更都要跨仓协调版本、跨仓等待 CI，且"引擎改了、App 没跟上"这类事故会反复发生。

## 决策

**采用 monorepo**：引擎、SDK、双端应用、工具、基准放在同一仓库，共用一套 CI 与版本标签。

## 备选方案

| 方案 | 优点 | 缺点 | 为什么没选 |
| --- | --- | --- | --- |
| 多仓（engine / sdk / apps 分开） | 权限清晰、仓库轻、SDK 可独立发版 | 接口变更跨仓协调成本高；CI 无法端到端验证；早期极易版本错配 | 团队 <10 人时协调成本远大于收益 |
| monorepo + 子模块 | 兼顾隔离 | 子模块指针管理繁琐，CI 需递归拉取 | 复杂度不值 |
| 单仓但物理分目录 + 独立发布流水线 | — | — | **即本方案** |

## 后果

正面：

- 一个 PR 可以同时改引擎 ABI 与两端调用点，CI 一次验证。
- 版本号、依赖、代码风格、许可证审计统一。
- 新人 clone 一次就能跑通全链路。

负面 / 代价：

- 仓库体积会随模型与测试数据增长，需严格 `.gitignore` 与 LFS 策略。
- CI 需要路径过滤（`paths:`），否则每个 PR 都跑全平台构建，成本爆炸。
- 权限粒度变粗，外部贡献者需要 CODEOWNERS + 目录级保护。

需要跟进：

- [ ] CI 按路径触发（M0）
- [ ] 大文件走 Git LFS 或对象存储，禁止直接 commit 权重（M0）
- [ ] SDK 对外稳定（M4）后评估是否拆出 `sdk/` 独立发版

## 复审条件

- 团队规模 > 25 人，或外部贡献者 > 10 人；
- 单次 clone 时间 > 5 分钟；
- CI 平均等待 > 20 分钟且无法通过路径过滤解决。
