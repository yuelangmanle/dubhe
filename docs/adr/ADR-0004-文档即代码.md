# ADR-0004: 文档即代码（开发书与进度书纳入 Git）

- 状态：Accepted
- 日期：2026-10-29
- 决策者：Tech Lead
- 关联：DUBHE-DEV-000 §6.6

## 背景

项目从立项第一天就要维护两类文档：**开发书**（我们要造什么、怎么造、怎么验收）与**进度书**（现在到哪了、卡在哪）。

常见做法是把它们放在在线文档里。问题是：

- 与代码脱节，改了接口不改文档，半年后文档全是错的；
- 无法回答"三个月前我们为什么这么决策"；
- 评审时无法 diff，只能看"最终版"；
- 无法与发布 tag 对齐（v0.5 发布时的规格是什么？）。

## 决策

**文档以 Markdown 形式存放在仓库 `docs/`，Git 是唯一真相来源。**

具体规则：

1. 开发书、进度书、ADR、RFC 全部入 Git，与代码同 PR 评审。
2. 需要排版版（对外评审、给非工程方看）时，用脚本从 Markdown 生成 docx；**docx 是产物，不是源**，回填到 `docs/references/` 作为归档。
3. 里程碑评审打 tag（`docs/m0-review`），形成可回溯的时间线。
4. 进度书每周一次 commit（`docs(progress): W12 weekly log`），只追加不覆盖。
5. ADR 只追加，决策变更写新条目并标注 Supersedes。

## 备选方案

| 方案 | 优点 | 缺点 | 为什么没选 |
| --- | --- | --- | --- |
| 在线文档（飞书/Notion） | 协作好、评论方便 | 与代码分离、无 diff、无版本对齐 | 违背"文档与代码同源" |
| docx 直接入 Git | 排版好 | 二进制无法 diff，冲突无法解决，历史不可读 | 版本管理基本失效 |
| Markdown + 生成 docx（本方案） | 可 diff、可评审、可发布 | 需要维护生成脚本 | **本方案** |
| 文档站（静态生成） | 对外友好 | 早期投入过大 | M5 后再考虑 |

## 后果

正面：

- 每个决策都能追溯到"谁、何时、为什么"。
- 文档滞后可以被 CI 发现（例如 ABI 头文件变更但 `sdk/README` 未更新）。
- 发布版本与规格版本一一对应。

负面 / 代价：

- 需要维护 `tools/docs/build_docx.sh` 与模板样式。
- 团队成员要接受"改行为必须改文档"的纪律，前期会有摩擦。

需要跟进：

- [ ] 编写 `tools/docs/build_docx.sh`（M0）
- [ ] PR 模板加"文档影响"必填项（M0）
- [ ] CI 检查：`engine/include/dubhe/*.h` 变更时 `docs/` 必须有对应改动（M1）

## 复审条件

- 若团队规模扩大导致 Markdown 协作冲突频繁（每周 > 3 次），引入文档站或拆分文件粒度。
