# ADR-0005: 引擎运行在独立进程，零拷贝 IPC

- 状态：**Deferred（推迟到 M5）**
- 日期：2026-10-29
- 决策者：Tech Lead
- 关联：DUBHE-DEV-000 §4.2

> **v2 修订（2026-10-29）**：本决策推迟到 M5 做 App 时再落地。
> 理由：M0–M4 只有 CLI 与 `dubhed`，没有 UI 进程可拖累；单进程能让调试、profiling、数值比对简单一个数量级。
> 过早拆进程是典型的架构过度设计——IPC 协议、无锁 ring buffer、跨版本兼容，每一样都是 bug 温床，而首期收益为零。
> **但设计上仍保留这个可能性**：引擎内部不得依赖"全局唯一实例"或"进程级单例"，以便将来无痛拆分。

## 背景

引擎是一个"吃内存、跑满 GPU、可能 OOM、可能被系统杀"的组件。宿主是"要流畅、要响应、不能崩"的 UI 进程。把两者放在同一进程，有三个具体问题：

1. **内存隔离失效**：4B 模型 + 32k 上下文可能占 6 GB，一旦 OOM，整个 App 被系统杀掉，用户丢失会话。
2. **崩溃半径过大**：一个 Metal Kernel 越界直接带走 UI。
3. **无法共享**：未来多个 App（或 App + CLI）想复用同一个已加载模型，进程内方案做不到。

## 决策

**引擎运行在独立进程**，宿主通过 IPC 调用：

- macOS：XPC Service（`com.dubhe.engine`），系统托管生命周期。
- Android：前台 Service + `android:process=":engine"`，AIDL/Binder 接口。
- **token 流走共享内存 ring buffer**，不走逐 token 的 RPC 回调（否则延迟抖动不可接受）。
- 模型权重只 mmap 一次，共享给两侧只读视图，不复制。

## 备选方案

| 方案 | 优点 | 缺点 | 为什么没选 |
| --- | --- | --- | --- |
| 同进程静态库 | 零 IPC 开销，最简单 | OOM/崩溃直接带走 UI；无法多客户端共享 | 风险不可接受 |
| 独立进程 + 逐 token RPC | 实现简单 | 每 token 一次跨进程调用，ITL 抖动 +0.2–0.5 ms，decode 场景致命 | 性能不可接受 |
| **独立进程 + 共享内存流** | 隔离 + 低延迟 | 需要自己管 ring buffer 与生命周期 | **本方案** |
| 本地 HTTP（localhost） | 通用、跨语言 | 内核态网络栈开销、端口冲突、防火墙 | 仅用于 `dubhed` 对外，不用于宿主↔引擎 |

## 后果

正面：

- 引擎崩溃可被宿主检测并重建（配合 state checkpoint，用户几乎无感）。
- 内存可被系统按进程回收，Android 上更容易通过后台策略审核。
- 为"一个引擎服务多个客户端"留出空间。

负面 / 代价：

- 需要设计一套 IPC 协议与版本协商（引擎版本 ≠ 宿主版本时必须兼容）。
- 调试变复杂（跨进程采样、日志聚合）。
- 共享内存 ring buffer 的同步原语要自己写（无锁或 futex），是 bug 高发区。

需要跟进：

- [ ] IPC 协议 v1 定义（消息类型、超时、背压、错误码）（M1）
- [ ] ring buffer 的无锁实现 + 压力测试（M2）
- [ ] 跨版本兼容策略：引擎与宿主版本不一致时的降级路径（M2）
- [ ] Android 前台服务类型声明与通知策略（M3）

## 复审条件

- 若 IPC 引入的端到端延迟 > 0.3 ms/token，或 ring buffer 在 8 路并发下出现数据竞争；
- 若平台政策禁止常驻独立进程（商店审核失败）。
