# ADR-0006: 许可证策略——引擎 Apache-2.0，应用商业许可

- 状态：Proposed（需法务确认，M0 评审定稿）
- 日期：2026-10-29
- 决策者：Tech Lead + 法务
- 关联：AETHER-DEV-000 §11.3、§12.1

## 背景

引擎大量参考/复用 MIT（llama.cpp）、Apache-2.0（Locals、vLLM Metal、MNN、MLC-LLM、LiteRT-LM）、BSD（ExecuTorch）项目的代码与思想。

同时产品需要商业化，且本地 AI 用户对"闭源引擎会不会偷传数据"极度敏感。

## 决策

| 组件 | 许可 |
| --- | --- |
| Engine / AetherKit / Studio | **Apache-2.0**（含专利授权条款） |
| Desktop / Mobile | 商业许可（源码可见可选） |
| 企业特性 | 商业许可 |
| 厂商 SDK（QNN / MediaTek） | 不打包，作为可选动态插件 |

三条硬约束：

1. **禁止** GPL/AGPL 代码进入任何交付二进制（含静态链接），CI 强制扫描。
2. 所有第三方代码进 `THIRD_PARTY_NOTICES.md` 与 SBOM，保留原始版权头。
3. 模型许可与引擎许可**彻底分离**：模型许可记录在 `manifest.json`，与应用许可无关。

## 备选方案

| 方案 | 优点 | 缺点 | 为什么没选 |
| --- | --- | --- | --- |
| 全闭源 | 商业保护强 | 无法自证隐私；难以被集成；社区不信任 | 与产品核心承诺冲突 |
| 全 Apache-2.0（含应用） | 社区最大化 | 无变现路径 | 无法支撑 14 个月研发 |
| **open-core（本方案）** | 信任 + 变现兼顾 | 需明确边界，避免"开源版故意阉割"的舆论 | **本方案** |
| BSL / 延迟开源 | 保护商业 | 不是 OSI 许可，企业客户排斥 | 得不偿失 |

## 后果

正面：

- 引擎可被第三方集成，形成生态入口。
- 隐私承诺可被外部审计，"不开源"的质疑直接消解。
- Apache-2.0 与多数参考项目兼容，法律摩擦最小。

负面 / 代价：

- 竞争者可以直接使用引擎（但拿不到应用层与 autotune 数据资产）。
- 需要维护 CLA / DCO 流程，否则无法接受外部贡献。
- 必须持续投入合规工程（SBOM、扫描、NOTICE 生成）。

需要跟进：

- [ ] 法务确认 Apache-2.0 与全部参考项目的兼容性（M0）
- [ ] `LICENSE`、`NOTICE`、`THIRD_PARTY_NOTICES.md` 建立（M0 任务 #13）
- [ ] CLA/DCO 流程与 CONTRIBUTING 文档（M1）
- [ ] 商标注册（"Aether" 通用词，需检索避让）（M0 任务 #17）

## 复审条件

- 若法务认定某关键依赖与 Apache-2.0 不兼容（如必须链接 GPL 组件）；
- 若商业验证显示 open-core 无法支撑收入，需重新评估应用层许可。
