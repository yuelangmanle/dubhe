# ADR-0006: 许可证策略——全闭源，保留开源复审条件

- 状态：Accepted（**v2，取代 v1 的 open-core 方案**）
- 日期：2026-10-29
- 决策者：你（产品负责人）
- 关联：DUBHE-DEV-000 §11

## 背景

v1 的方案是 open-core（引擎 Apache-2.0，应用商业许可），理由是"本地 AI 用户不信任闭源引擎"。

但项目当前的真实状态是：**单人 + AI 开发，还没有任何技术验证**。此时开源只会带来两个后果：

1. 在没有护城河的时候把设计细节全部交出去；
2. 维护开源协作（Issue、PR、CLA、双语文档）要吃掉本就有限的精力。

## 决策

**全闭源（Proprietary，All rights reserved）**，仓库私有。但**允许且合法地复用宽松许可的开源代码**：

| 来源许可 | 可否复用 | 条件 |
| --- | --- | --- |
| MIT（llama.cpp） | ✅ | 保留版权声明，进 `THIRD_PARTY_NOTICES.md` |
| Apache-2.0（MLX、vLLM Metal、MNN、MLC-LLM、LiteRT-LM） | ✅ | 保留 LICENSE / NOTICE；Apache-2.0 **允许闭源分发** |
| BSD-3（ExecuTorch） | ✅ | 保留版权声明 |
| GPL / AGPL / LGPL（静态链接） | ❌ | 传染，CI 强制扫描阻断 |

## 关键澄清（很多人在这里搞错）

> **"闭源"和"用开源代码"不冲突。** MIT / Apache-2.0 / BSD 都明确允许闭源商用，只要求保留声明。
> 真正冲突的只有 GPL 系——静态链接即传染，动态链接也基本逃不掉。
> 所以本项目的合规底线不是"不用开源"，而是"**不用 copyleft**"。

## 备选方案

| 方案 | 优点 | 缺点 | 为什么没选 |
| --- | --- | --- | --- |
| open-core（v1 方案） | 建立信任、可被集成 | 无护城河时开源等于送设计；维护成本高 | 现阶段性价比低 |
| 全开源 | 社区最大化 | 无收入路径，且当前无社区可运营 | 不适用 |
| **全闭源 + 保留复审**（本方案） | 保护早期投入，精力集中在技术上 | 借不到社区力量；"会不会偷数据"只能靠行为证明 | **本方案** |
| BSL / 延迟开源 | 兼顾 | 非 OSI 许可，未来开源会有历史包袱 | 不如直接闭源干净 |

## 后果

正面：

- 设计细节（三图 IR、state 语义、autotune key）不外泄。
- 不需要维护 CLA、贡献者指南、双语文档。
- 复用 MIT / Apache 代码完全合法，技术路线不受影响。

负面 / 代价：

- 失去"可审计"这一信任背书，未来面向企业客户时要另想办法（第三方审计、源码托管）。
- 无法接受外部 Kernel 贡献——而 Kernel 恰恰是最需要人力的部分。
- 一旦将来开源，历史 commit 里的第三方代码 provenance 必须干净（所以现在就要记 SBOM）。

需要跟进：

- [ ] `LICENSE`（Proprietary 文本）+ `THIRD_PARTY_NOTICES.md`（M0）
- [ ] CI license 扫描：依赖白名单 + GPL 检测（M0）
- [ ] 每引入一个上游文件，记录 `来源仓库 + commit + 许可`（M0 起持续）

## 复审条件（明确写死，避免"永远闭源"变成惯性）

满足**任意两条**即重新评估开源：

1. M3 结束，引擎在 DubheBench 上稳定进入第一梯队（说明护城河已成立）；
2. 出现 ≥ 3 个外部开发者主动要求贡献 Kernel；
3. 企业客户明确要求源码审计；
4. 商业化验证失败，需要靠社区影响力换取其他路径。

复审时优先考虑：**引擎开源（Apache-2.0）+ 应用闭源**，即回到 v1 方案。
