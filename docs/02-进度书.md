## 9. M0 实施记录（已完成）

环境：Apple M4 / 24 GB / macOS 27.0.1 / Apple clang 21。
测试模型：`Qwen2.5-0.5B-Instruct-Q4_K_M.gguf`（Qwen 官方发布，182 MB，
量化组合 F32+Q5_0+Q8_0+Q4_K+Q6_K —— 注意它不是"纯 Q4_K"，实际是混合量化）。

### M0 / Round 1 · 引擎骨架跑通

**交付**
- `engine/include/dubhe/dubhe.h` C ABI（版本 0.1.0）
- `engine/src/{gguf,quant,tokenizer,model,engine}.cpp`
- `cli/main.cpp`（inspect / run / chat / bench）
- `Makefile`（零外部依赖，clang++ -std=c++20）

**验证**
```
$ make && ./build/dubhe inspect <model>
架构 qwen2 · 24 层 · 896 维 · 14 头(KV 2) · 词表 151936 · ChatML
```

**踩到的坑（都是真实 bug，已修）**
1. `byte_to_char_` 对 161–255 的字节用了原始字节，而 GPT-2 的映射是"码位"，
   必须写出 UTF-8 编码（如 228 → `ä` = C3 A4）。否则中文全部切不开。
2. BPE 的初始符号必须是**字节**，不是 UTF-8 字符。原来按字符切，一个汉字被
   当成一个符号，merges 永远不命中。
3. `Makefile` 没有头文件依赖跟踪。改 `internal.h`（结构体加了成员）后只有部分
   `.o` 重编，`Model` 的布局在两个编译单元里不一致 → 一加载就段错误，
   堆栈还指向完全无关的 `build_byte_map`。已加 `-MMD -MP`。
4. KV cache 按训练上下文（32768）预分配 = 805 MB。改成从 1024 起按需翻倍。
5. `<|im_end|>` 被当成正文输出。EOS 判断必须在回调**之前**，且所有
   CONTROL/USER_DEFINED 类型的 token 都不能吐给用户。

**性能**：decode 7.7 tok/s（纯标量 f32 内核）。

### M0 / Round 2 · 内核 SIMD 化

**交付**
- `engine/src/quant_q8.cpp`：量化激活（Q8_0）+ ARM NEON 整数点积
- `tests/test_quant.cpp`：11 种类型的位解包自检 + 整数路径一致性自检
- `bench/matvec_bench.cpp`：按真实模型形状测各类型吞吐

**做法**：把激活也量化成 int8，两边都用 `vdotq_s32`（一条指令 16 次乘加），
K-quant 的 `-dmin·m` 偏置项拆成 `Σ q·a` 和 `Σ a` 两项分别算。

**验证**
```
$ ./build/test_quant
=== 内核位解包自检 ===  全部通过（相对误差 ≤ 1.6e-7）
=== 整数点积路径自检 === 全部通过（相对误差 ≤ 9.1e-4，属于激活量化噪声）
```

**效果**

| 形状 | 类型 | f32 | q8 | 加速 |
| --- | --- | --- | --- | --- |
| ffn_down 896×4864 | Q6_K | 0.669 ms | 0.178 ms | 3.75x |
| attn_q 896×896 | Q5_0 | 0.188 ms | 0.111 ms | 1.69x |
| out_w 151936×896 | Q8_0 | 15.115 ms | 10.468 ms | 1.44x |
| ffn_gate 4864×896 | Q5_0 | 0.657 ms | 0.412 ms | 1.59x |

**端到端**：7.7 → 20.0 tok/s（2.6x）。

**注意（重要）**：本机顺序读带宽实测只有 **17 GB/s**（真实 M4 应在 100 GB/s
量级），说明当前运行环境本身受限，绝对值不可作为真机结论。加速比可信。

## 9.5 M1 实施记录：Metal GPU 后端（Round 4，已完成）

### 目标与结果

目标是把矩阵乘搬到 GPU。结果比预期好，但过程推翻了我最初的设计。

| 指标 | CPU (NEON) | Metal GPU | 倍数 |
| --- | --- | --- | --- |
| decode | 20.6 tok/s | **60.9 tok/s** | 2.96x |
| prefill | 21.3 tok/s | **70.0 tok/s** | 3.29x |
| 与纯 f32 基准的 logits 最大差 | 3e-2 | **1e-4** | GPU 更准 |

GPU 路径的 logits 反而比 CPU 更接近纯 f32 基准——因为 CPU 默认路径把激活
量化成 Q8（快 2~4 倍，代价是 ~1e-3 相对误差），GPU 用的是 f32 激活。
**所以验收 GPU 数值必须关掉 CPU 的 Q8 路径**（`DUBHE_F32_REF=1`），
否则量到的是 CPU 自己的近似误差。

### 第一步走错：逐 matvec 同步只快 8%

第一版实现是"每次 matvec 提交一个 command buffer 并等待"，架构上最直观。
实测只比 CPU 快 8%（22 vs 20.3 tok/s）。

量了一下才明白：

```
GPU 读带宽        47 GB/s
commit+wait 延迟  201 µs      ← 真正的瓶颈
```

0.5B 模型单 token 有 169 次 matvec（24 层 × 7 + 1），逐次同步 = **34 ms**
纯等同步。GPU 算力（约 3.5 ms/token）完全被埋在同步里。

### 正确做法：整层前向编进一个 command buffer

把 rmsnorm / rope / attention / silu / 残差 / bias 全部写成 Metal 融合算子，
和 7 个量化 matvec 内核一起编进**同一个** command buffer，每 token 只同步一次。
同步开销从 34 ms 降到 0.2 ms。

代价：CPU 侧的 glue（rmsnorm、attention 等）也要搬到 GPU，否则会出现
"GPU 算完 → CPU 读回 → 再提交"的往返。所以 `forward()` 在 GPU 模式下
是一条独立的执行路径，CPU 路径完整保留作为数值基准（oracle）。

### 三个设计决定

1. **运行时编译 MSL**（`newLibraryWithSource:`）。离线 Metal Toolchain 一直
   没装成功（`xcodebuild -downloadComponent MetalToolchain`），但运行时编译
   完全可用，代价是加载时多 ~200 ms。这条绕开方案让项目不必被工具链卡住。
2. **权重零拷贝**：整块 mmap 直接包成 `MTLStorageModeShared` buffer，每张量
   用字节偏移定位（绕开 `setBuffer:offset:` 的 256 字节对齐限制）。内存占用
   与 CPU 路径完全相同。
3. **加载期交叉校验**：用真实权重跑 GPU vs 纯 f32 基准，相对误差 > 1e-3 就
   整体退回 CPU。手写位解包一旦某个 nibble 位移写错，模型会"能跑但胡言乱语"，
   这种 bug 从输出上几乎看不出来，必须靠自检拦。

### 抓到的两个真 bug

- **`k_attn` 在线 softmax 忘了缩放累加器**。最大值更新时只缩放了分母 `l`，
  没有同步缩放已累加的 `acc`。症状很迷惑：部分 head 输出完全正确、部分错，
  取决于数据（当最大值恰好是第一个 key 时结果就是对的）。输出是乱码但程序
  不崩、不报错。这是 flash-attention 最经典的坑。
- **MSL 里 `half` 是内建类型名**，不能当变量名用（`const uint half = hd/2;`
  报 "cannot combine with previous 'type-name'"）。

### 调试方法沉淀

写了两层对拍工具，都不进正式构建但很有用：

- **单算子对拍**：把每个融合内核单独拉出来和 C 参考实现比。这次一眼看出
  只有 `k_attn` 错（其余全是 1e-7 量级），省掉大量猜测。
- **逐位置 logits 对拍**：CPU / GPU 各跑一遍同样的 prompt，逐 token 比
  argmax、maxerr、cosine。argmax 全一致 + cos=1.000000 才算过。

### 当前瓶颈与下一轮

GPU 现在跑到带宽的 ~57%（0.4 GB 权重 / 15 ms ≈ 27 GB/s，实测上限 47 GB/s）。
主要原因是 **matvec 的并行度太低**：一个线程算一行，`ffn_down` 只有 896 个
线程，10 核 GPU 根本喂不饱。

### 下一轮（Round 5）候选，按优先级

1. **matvec 提高并行度**：一行拆给多个线程（threadgroup 内 4 行 × 8 线程，
   用 `simd_shuffle_xor` 归约），预计 1.5–2x。
2. **prefill 批处理**（n_batch > 1）。现在 prefill 是一个 token 一个 token 算，
   长 prompt 首字延迟很难看——这是产品体验上最大的短板。
3. **Q5_K 的整数内核**（CPU 侧目前走 f32 路径，功能对但不快）。
4. **agent 循环**：多轮工具调用 + 计划-执行-反思，参考 Claude Code / opencode
   的工具协议。
5. **Android**：NDK 交叉编译 + NEON 已经是通的，缺 NPU（QNN/NeuroPilot）接入。

### 环境待办

- `xcodebuild -downloadComponent MetalToolchain`（约 1–2 GB，未完成；已绕开）
- 第二台机器（骁龙 8 至尊版 / 天玑 9400）的交叉编译验证

## 9.6 M1 实施记录：底层三处结构性优化（Round 5，已完成）

这一轮没有加功能，只动底层。三处改动、两个真 bug、一套新的测量方法。

### 先说测量方法：绝对数字不可信，只信交替对比

这台机器的绝对性能波动极大（load average 4.5，且此前测出裸带宽只有
17 GB/s，真实 M4 应在 100 GB/s 量级——说明运行环境本身被限制）。同一份
二进制连跑 5 次，decode 能从 83 掉到 51。

所以这一轮改用 **git worktree + 背靠背交替测量**：把上一版 commit 编译到
另一个目录，然后"旧 → 新 → 旧 → 新"交替跑。这样热降频和背景负载对新旧
两版的影响大致相同，倍数才可信。下面所有倍数都是这么测的。

### 优化一：matvec 从"一线程一行"改成"一个 simdgroup 一行"

原来的并行粒度是一个线程算一行输出。`ffn_down` 只有 896 行 → 只发出 896
个线程，而 M4 有 10 核 × 128 = 1280 个 ALU 槽位。更要命的是每个线程背着
一串**串行依赖**的 load（896 个元素要顺序读 28 个量化块），延迟完全暴露。

改成一个 simdgroup（32 lane）算一行：lane 分摊行内元素，最后 `simd_sum`
归约。并行度 ×32（28672 线程），且同一时刻 32 个 lane 读的是行内相邻数据。

lane 分工必须贴合量化格式的布局，否则解码会绕远路：
- 32 元块（Q4_0/Q5_0/Q8_0）：一个块正好 32 元素 → lane 就是块内下标，
  低 16 个元素取低半字节、高 16 个取高半字节。
- 256 元块（Q4_K/Q6_K）：块内分 8（或 16）个小段，lane 在每个小段各取
  一个元素 → 天然对应 scale 的布局。

顺带一个化简：Q4_K 的 min 项不必单独对 x 求和，可以折进逐元素 fma ——
`Σ(d·sc·v − dm·m)·x` 与 `d·sc·Σ(v·x) − dm·m·Σx` 等价，少一遍规约。

### 优化二：prefill 批处理（这是 TTFT 的关键）

解码时每个 token 必须把 0.4 GB 权重全读一遍，带宽就是天花板。批处理把
同一遍读取摊到 8 个 token 上，权重算术强度 ×8。

三个设计决定：

1. **单独的 mm_* 内核**，不复用 mv_*。解码内核一行都改不了，只能另写一套。
   这是刻意接受的重复。
2. **激活转置成 `[n_in][BMAX]`**。第一版直接按 `X[j][e]` 取，每个权重值要发
   8 条标量加载；转置后 8 个激活连续，变成两条 `float4`。prefill 从
   205 → 385 tok/s（+87%）。
3. **转置时对 `j >= nrow` 填 0**，于是内核里可以彻底去掉 `if (j < nrow)`
   的分支，8 次 fma 无条件做满。

还顺手省掉了 prefill 的 `out_w`：只有最后一行需要 logits，而 `out_w` 是
全模型最大的单个矩阵乘（占权重流量 36%）。

### 优化三：split-K 注意力（长上下文是更严重的坑）

改完前两处之后测长上下文，发现一个比 prefill 更严重的问题：

```
631 token 上下文   decode 31.9 tok/s   （短上下文 83 tok/s）
```

注意力内核一个 head 一个 simdgroup，0.5B 只有 14 个 head = 448 线程，而
有 40 个 SIMD 单元。于是每个 SIMD 单元上只挂一个 simdgroup，**零延迟掩盖**：
每次 key 迭代里的 `simd_sum`（5 步 shuffle）和 `exp` 都串行暴露在关键路径
上。631 个 key × 24 层 = 18 ms/token 纯等待。

解法是 flash-decoding 的 split-K：把 key 区间切成 nsp 段并行算局部
(m, l, acc)，再用一个很轻的 combine 内核按 `exp(m_i − M)` 归并。
nsp 随上下文长度增长（`nlen/96`，上限 8）。

批处理时每行可见长度不同（行 r 是 `pos0+r+1`），短的那些行会算出空区间。
处理办法是空区间写 `m=-1e30 / l=0`，combine 里 `exp(-1e30 - M) = 0` 自然
不参与归并——不需要任何特判。

**一个反直觉的教训**：split-K 在 `nsp == 1` 时是纯亏的（多一次 partial
缓冲往返 + 一次 combine dispatch），实测把短上下文 decode 拖低了 25%。
所以保留了原来的融合版内核，`nsp == 1` 走它，`nsp > 1` 才走 split。

### 抓到的两个真 bug

- **公共 lambda 忘了绑 buffer**。把 `add` / `silu` 收进一个只
  `setComputePipelineState` 的公共 lambda 之后，`k_add` 读到的是上一次
  `gemm` 留下的绑定——`d` 竟然指向权重 mmap。症状是"输出等于输入
  embedding"（模型只会重复你说的话）。因为权重是 `PROT_READ` 只读映射，
  误写没有破坏文件，但这是个运气。
- **原地 rmsnorm 的 aliasing**。最后一层的 norm 一开始写成 `out == x`。
  MSL 里 `device const float*` 与 `device float*` 指向同一块缓冲时编译器
  可以假设不重叠。改成独立的 `g_bfinal` 缓冲，不留悬念。

### 新增工具：`make optest`

整个前向是 400 多个 dispatch 编进一个 command buffer，错一个的症状只有
"输出乱码"，从外面完全看不出是哪个。`tools/gpu_optest.mm` 把 7 个融合算子
（rmsnorm / add / bias / silu / rope / copy / attn）单独拉出来和 C 参考实现
逐个比，包括 `rows=1/3`、`nsp=1/4`、不同 head_dim 的组合。

这一轮就是靠它一眼确认"7 个算子全对"，从而把嫌疑范围从"某个算子"收敛到
"绑定顺序"，直接找到了那个 lambda。

### 下一轮（Round 6）候选，按优先级

1. **agent 多轮循环**：现在只支持一轮工具调用。产品形态上这是最大的缺口。
2. **Q5_K 的整数内核**（CPU 侧目前走 f32，功能对但不快）。
3. **BMAX 提到 16**：权重读取的复用率再翻倍。代价是 16 个累加器 + 4 个
